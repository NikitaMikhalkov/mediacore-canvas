# Mediacore 执行方案

本文件是本工程唯一执行入口。产品目标见[正式规格](mediacore-platform-spec.md)，任务状态与依赖只维护在 [Mediacore Linear 项目](https://linear.app/nikita96/project/mediacore-1d6254ea120c)。研究报告和上游设计文档提供事实与实现背景，不构成本项目开发清单。

独立玻璃材质原型已完成，用户选定 A「忠实磨砂」，现已授权按当前票实施并使用 Subagent 并行开发。执行仅覆盖原生验证、现有配置和必要局部调整；真实模型付费调用、部署和生产验收仍属后续范围。设计原型可使用 Astra；机械核查可交由 6 Luna。原型选择、源码验证、部署与用户验收分别留证。

## 执行规则

依据 [ADR-0014](../adr/0014-minimal-reuse-no-custom-systems.md)，每项工作按以下顺序判断：

1. **验证现有行为。** 找到现有入口、配置及相关测试，复用已有证据；只补必要验证。已经满足需求即可零产品代码变更完成，不为其创建开发任务。
2. **使用现有配置。** 优先配置渠道、现成协议插件、模型、价格、配额、会话及外观。记录配置位置和实际行为，配置保存成功不等于功能验收通过。
3. **做必要局部调整。** 限于已确认的品牌、玻璃样式、密码步骤、期限和展示等调整，沿用既有组件、接口与服务。实际缺陷先定位最小修复点，不借机重构。
4. **记录能力差异。** 若需要新协议流程、状态机或业务系统，记录原行为、目标、现成可选方案和影响，保持待决。不自研缺失能力，也不通过迁入另一套系统绕过此限制。
5. **按证据交付。** 区分已满足、可配置、需局部调整、待决、未验证；任务只覆盖实际工作。未解决的收费或权限差异不宣称通过，不默认开放相关路径。

## 能力、最小工作与验收

以下“现有能力”为固定基线的静态调查结论，并非运行验收。各行是工作边界，不要求逐行新增任务。

| 范围 | 现有能力 | 最小工作 | 完成证明 |
| --- | --- | --- | --- |
| 多用户与工程 | 账号归属、用户缓存作用域、工程/资源/任务权限 | 验证保存、重开、切换与删除 | 双账号互换标识、旧请求和并行标签页不串数据；删除后各入口一致 |
| 邮箱认证 | 注册、验证码、找回、哈希与会话撤销 | 配置邮件、公开注册和零初始积分；沿原流程拆出密码步骤；七天会话优先配置 | 完整注册/找回、验证码边界、Cookie 与服务端期限、退出/重置失效；需要新认证协议时列差异 |
| 渠道与模型 | 管理员渠道、加密密钥、模型发现、逻辑模型与协议插件 | 配置 4aion 的 URL、鉴权、模型和字段；关闭个人渠道绕过；纯模型名展示 | 普通用户仅用平台模型，密钥不出后端；核对真正生效的插件与请求 |
| 创作入口 | Agent、文本、图片、视频、音频、转写已有入口 | 按协议族复用现成适配并逐模型验证；不兼容入口暂不开放 | 记录实际输入输出、参考素材、流式/工具调用、usage、查询/取消与回存；发现模型不等于可用 |
| 积分与运营 | 成本价格档、倍率、快照、冻结/结算/退款、发放及兑换码 | 配置可信成本与统一倍率，验证原账本；真实支付显示暂未开放 | 价格快照、计量/舍入、改价、余额不足、重复处理和兑换行为可核对 |
| Agent 与任务 | 工具、预算、审批、持久任务、租约、查询、待核对与取消 | 验证原授权、恢复和限流；不新增调度机制 | 未知不重发，停止不等于远端取消；整批授权、失败依赖和在途限额不足则列差异 |
| 资源、分享与配额 | 回存恢复、引用生命周期、实时只读分享、期限/撤销、用户配额 | 默认七天分享及实时更新提示、配额配置与现有权限验证 | 保留原分享内容；Agent 聊天不公开；到期/撤销失效；达配额保留既有素材读/下载/删除 |
| 品牌与玻璃 UI | 外观配置、token、AntD 与 Celadon/React Aria、已有页面和节点 | Mediacore 资产/文案与共享样式局部调整；保留组件、布局及位置 | 三种主题、全路由/浮层/节点/管理端、冷启动/失败/重置覆盖；媒体清晰、空态原 Icon、几何和性能对比 |
| 自有发行与服务器 | 现有构建、Compose、迁移、前端/Go/Node Agent/PG/Redis | 配置自有发布源、版本、环境、SMTP、存储及管理员 | 同版本可追溯；隔离、创作恢复、备份恢复和实际负载验证，不以健康检查代替验收 |

## 待决差异

这些目标仍保留，但不是新增实现任务。可通过原生配置或现有人工操作覆盖时，提供证据；不能覆盖时再由用户决定产品取舍。

| 目标 | 已知差异或待验证点 | 当前处理 |
| --- | --- | --- |
| 费用授权上限、无负余额 | 原文本可能超预留形成负余额，部分音频不同；输出预算不等于完整封顶 | [NIK-276](https://linear.app/nikita96/issue/NIK-276)：核对原生计费与配置，不补写封顶/平台差额机制 |
| 同次提交不重复消费 | 账务幂等与供应商 attempt key 不证明普通重复请求归并 | [NIK-277](https://linear.app/nikita96/issue/NIK-277)：调查现有接口行为，不新增提交协议或去重表 |
| 最终不可交付退款 | 已有回存恢复不证明所有最终失败均自动退款 | [NIK-279](https://linear.app/nikita96/issue/NIK-279)：核对现有释放/退款及管理员操作的覆盖 |
| 专用素材和转写接入 | 原素材鉴权/上传、转写协议与 4aion 有差异 | [NIK-275](https://linear.app/nikita96/issue/NIK-275)：只验证现成配置；不兼容模型或入口保持未开放 |
| 三个全平台媒体在途名额、每用户一个 | worker 并发不等于供应商在途数量 | 核对原生限流的真实语义；配置不足列差异，不另建队列 |
| Agent 整批授权、独立失败继续与依赖暂停 | 已有预算/审批不证明完整批次语义 | 核对现有工具与审批；不能覆盖时列差异，不另建 Agent 编排 |

差异没有解决不等于用户接受负余额、重复消费或交付失败收费。相应目标的验收必须如实标注未满足。

## 推进顺序

1. 确认独立基线及现有能力，复用已有测试验证关键用户路径。代码存在只能作为静态证据。
2. 配置平台供给、认证与运营参数；用不计费 fixture 验证已选择模型的协议和异常响应，同时处理差异清单。
3. 玻璃材质原型已比较三档方案，用户选定 A「忠实磨砂」。原型证据见 [NIK-272](https://linear.app/nikita96/issue/NIK-272)，独立分支 `prototype/mediacore-glass`、提交 `82308928`；使用真实组件与内存模拟数据，覆盖画布/节点、工具栏设置浮层、登录页及管理表格，不等于完整业务验收。
4. 正式换肤以 A 为基准，沿原 token 与共享控件做全站换肤、品牌和必要局部调整；先共享层再页面特例，避免重复样式和业务重写。基础/密集表面不透明度：浅色 64%/92%，深色 72%/94%，背景模糊 22px；沿用淡蓝紫环境光、细高光边界与轻阴影，保持媒体清晰、空态原 Icon 及既有组件几何。性能和可读性仍按真实页面验收，原型代码不直接合并为产品实现。用户已授权按当前票开发，缺失业务能力仍不自行实现。
5. 后续具备环境、模型范围和费用预算后，验证真实兼容性和服务器部署。当前阶段不执行。

Linear 已有任务原位维护；缺口使用 needs-info，原生验收、配置和设计任务按范围执行。需求总览 NIK-269 不作为另一个整站开发任务。后续只为已经识别的实际修改或验收建票，不为原生能力重复建功能开发票。

## 复用与并行执行约束

- **每票先声明复用对象。** 列出现有入口、组件或服务、可配置项、确需局部修改项和行为证据。能够沿用的直接沿用；不因切片需要展示完整路径而新增 schema、API、认证、账务或任务机制。共用样式已覆盖的页面只验收，未满足的业务能力仍按待决差异处理。
- **共享材质先形成可用基线。** 在真实画布主路径上落地 A 材质与必要共享适配，并验证基础节点、工具栏及浮层；不另建主题系统，不做预防性重构。其他方向可提前只读盘点和准备验收清单，页面样式改动从同一已验证提交开始。
- **按页面边界并行。** 共享基线具备后，创作工具与 Agent、工作台/设置/分享、管理后台、认证页面可以作为独立工作流，不互相串联阻塞。认证注册与登录找回两票由同一负责人顺序处理共同外壳和验证控件；确无共享写入的调查与原有会话验证可并行。
- **共享文件单一写入者。** 应用主题、皮肤 token、全局样式、共享浮层/控件与公共品牌配置由明确的整合负责人维护。页面负责人只改自己负责的页面与局部样式；需要共享调整时提交具体需求，由共享负责人统一落地。品牌票与材质票可并行调查、处理各自资产，但共用外观配置不得同时修改；不为避冲突复制 token 或新建平行组件。
- **隔离改动，统一整合。** 执行前约定每个工作流的写入范围、基线提交及验证责任，必要时使用独立 worktree。整合负责人将完成切片逐一合入唯一候选，每次复核受影响的已完成入口；后续共享变更使相关旧证据失效时补验。子任务完成不等于整站验收通过。
- **依赖只表示实际前置条件。** 视觉工作不被模型、账务或隔离验收无关阻塞；共享主题提交及本页面必需的品牌配置才构成对应交付前置。已有业务票可以先做原生核查，A 样式的最终验收需共享基线。标签表示任务可执行程度，不构成付费调用、部署或自研缺失业务能力的授权。

## 验证与上线条件

- 沿用真实 UI/已认证 API 和已有测试；针对变更或实际缺口补证据，不按旧架构提案制造接口和测试。
- 双用户隔离、认证七天边界、重复提交、余额不足、受理后断连、重启、取消未知、回存失败、重复结算/退款、批次失败和分享撤销均按真实路径观察。发现不满足目标时保留结果，不为了测试通过自行补业务机制。
- 同机同工程对比打开、拖拽/缩放、长任务、内存和保存延迟；十人同时编辑及三媒体任务是待验证负载目标。供应商等待、排队与前端耗时分别记录。
- 首期沿用单业务后端和原服务编排。验证独立 PG/Redis/存储、HTTPS/CORS、可信代理、SMTP、受控管理员、后端密钥保护及媒体运行时；数据库、素材与加密根材料共同备份并演练恢复。
- 固定前端/后端/Agent/迁移的自有版本，上游更新源改为自有或关闭。回退先停止新提交、保留在途核对；镜像回退不等于数据恢复。
- 许可证、法定署名及必要兼容标识保留；可选能力独立许可未满足时保持关闭。首期不接真实支付。
- 每项交付写明实际验证、失败、跳过及剩余差异；不把文档、原型或构建通过当作服务器和收费验收完成。
